顺便说一句你写代码的习惯

你写的是 if(step['type'] == 'text'):。逻辑完全正确，但那对括号是 JS 留下的肌肉记忆，Python 里不需要，直接写 if step["type"] == "text": 就行。hello.py 里也有同样的写法，所以这是习惯不是偶然。不影响运行，只是别人一眼能看出「这人从 JS 过来的」。课程末尾有个一次性解决的办法。

第一步：.venv 就是 node_modules

Python 默认把包装到系统全局，等于所有项目共用一个 node_modules。项目一多必然打架：A 要 anthropic==0.5，B 要 0.121，装谁都错。

虚拟环境就是解药，心智模型和 node_modules 完全一致：每个项目一份、可以随时删掉重建、不进版本库。

你熟的 Node今天要敲的 Python
（不需要，npm 自动建 node_modules）python3 -m venv .venv
建一次就够，之后不用再建
（不需要，node 自动往上找）source .venv/bin/activate
⚠️ 每开一个新终端都要重来一次
npm install anthropicpip install anthropic
npm lspip list
node index.jspython3 main.py
（无对应物）deactivate　退出虚拟环境

把这四行敲进终端：

终端 
# 确保在工作区根目录
cd /Applications/work/personal/study/pyhton-learn

python3 -m venv .venv
source .venv/bin/activate
pip install anthropic

成功的标志是提示符最前面多了 (.venv)。看不到它，就说明第二行没生效，装的包会跑到全局去。

最常见的一个坑

activate 只对当前这个终端窗口有效。关掉重开、或者换一个标签页，(.venv) 就没了，此时运行脚本会报 ModuleNotFoundError: No module named 'anthropic'。看到这个报错，第一反应应该是「我忘了 activate」，而不是「包没装上」。node_modules 不需要这一步，所以从前端过来的人几乎都会栽一次。

第二步：配好供应商（key ＋ base_url）

你手上的 key 是第三方中转的，所以除了 key，还得告诉 SDK 请求该发到哪个地址。

这一步值得单独讲，因为它比看起来重要得多：能随时换供应商，是接活交付的一项硬需求。客户可能因为价格、合规、网络环境指定用哪家。如果你把地址硬写在代码里，换一次就要改一遍代码。

官方 SDK 早就考虑了这件事。它默认会读这两个环境变量：

环境变量作用
ANTHROPIC_API_KEY密钥。不设就报认证错误
ANTHROPIC_BASE_URL请求发往的地址。不设就走 Anthropic 官方

所以 Python 代码一行都不用改，换供应商只是换环境变量。这不是我推测的，是查证过的两步：先在 SDK 源码里确认它会执行 os.environ.get("ANTHROPIC_BASE_URL")，再拿一个假 key 打到 Kimi 的端点，收到的是 Kimi 自己的报错文案而不是 Anthropic 的，说明请求确实路由过去了。

三种配置，选你手上有的那种

供应商要设的环境变量

模型：claude-haiku-4-5
第三方中转
← 你的情况		 ANTHROPIC_API_KEY ＋ ANTHROPIC_BASE_URL

第三方中转（你的情况）：

终端 
export ANTHROPIC_API_KEY="你的中转key"
export ANTHROPIC_BASE_URL="https://你的中转地址"

# 验证（应该各打印一行，不是空行）
echo $ANTHROPIC_API_KEY
echo $ANTHROPIC_BASE_URL

中转地址填到哪一层，取决于服务商的说明。SDK 会自己在后面接 /v1/messages，所以一般填到根路径就行，不要把 /v1/messages 也写进去，否则会 404。填错了自检脚本会告诉你。

换成 Kimi 的话（端点我实测存在，返回的是 Moonshot 自己的认证错误，说明路径对）：

终端 
export ANTHROPIC_API_KEY="你的Kimi key"
export ANTHROPIC_BASE_URL="https://api.moonshot.cn/anthropic"
export LESSON_MODEL="kimi-k3"

注意用 .cn 那个域名，api.moonshot.ai 从本机连不上。Kimi 提供的是 Anthropic 兼容端点，所以官方 anthropic SDK 直接就能用，不需要换成 OpenAI 的包。模型 ID 取自 Moonshot 官方文档（另有 kimi-k2.6、kimi-k2.7-code-highspeed 等）。

我的建议：先用第三方中转

理由是学习成本，不是质量。中转走的是 Anthropic 兼容协议，意味着你读到的每一份 Anthropic 官方文档、每一个 tool_use 的字段名，都能逐字套用，不用在脑子里做转换。下一课要接工具调用，字段一致会省掉很多困惑。
Kimi 留作备选：中转不稳、或者想省钱时切过去，反正只是改两个环境变量。把「能一键换供应商」当成你交付项目的默认架构，这是今天顺带学到的最值钱的一件事。

先跑自检，别急着做练习

配置类的问题最耗时间，所以我写了个自检脚本，把「装没装、设没设、通不通」一次性查完：

终端 
python3 exercises/00_check_env.py

它会打印 Python 版本、SDK 版本、遮掉中间的 key、实际使用的地址、模型名，然后发一个最小请求。看到「配置没问题」再往下做。报错的话它会分情况告诉你原因（401 是 key 和地址不匹配、404 是模型名不对、连不上是地址错），比直接看 SDK 抛的栈清楚得多。

以后任何一节课出问题，第一步都回来跑它。

交付视角：key 为什么绝不写进代码

你会看到很多教程直接 api_key="sk-..." 写在源文件里。别学。你要接活交付，代码最终会进客户的仓库。密钥一旦被提交，即使后来删掉，它永远躺在 git 历史里。GitHub 上有专门扫密钥的爬虫，泄露到盗刷通常是分钟级。

但要说清楚一件事：环境变量并不加密，它就是明文。它解决的唯一问题是让密钥不进版本库。所以我顺手给你建了 .gitignore，把 .venv/、__pycache__/、.env 都排除掉了。
还有：别把 key 粘到我们的对话里。你不需要给我看，我也不该看到。

环境变量只在当前终端有效。想长期生效，把那几行 export 追加到 ~/.zshrc，然后 source ~/.zshrc。

第三步：发出第一个请求

只有三个必填参数。我查了 SDK 的真实函数签名来确认这一点，不是凭印象写的：

参数作用
model用哪个模型。练习脚本从 LESSON_MODEL 环境变量读，默认 claude-haiku-4-5。模型名归供应商管，换家就得换名
max_tokens最多让它输出多少 token。必填，这是防止一次回复烧掉大量成本的安全阀
messages对话历史，一个列表。每项是 {"role": ..., "content": ...}

role 只有两个值需要现在关心："user"（你说的）和 "assistant"（模型说的）。

第一个反直觉点：回复不是字符串，而且第一块不一定是文字

resp.content 是一个内容块的列表。为什么？因为一次回复可能同时装着好几种东西，每种是一个块：

块类型type 的值内容在哪
文字"text".text
思考过程"thinking".thinking　没有 .text
工具调用请求"tool_use".name 和 .input

所以不能写 resp.content[0].text。思考型模型（kimi-k3 就是）会把 thinking 块放在最前面，那样写会直接抛 AttributeError: 'ThinkingBlock' object has no attribute 'text'。

正确做法是按类型筛：

text = "".join(b.text for b in resp.content if b.type == "text")

# TS 类比：
# content.filter(b => b.type === "text").map(b => b.text).join("")

这个设计下一课就会派上用场：届时你会在同一个 content 里同时看到 text 块和 tool_use 块，而按类型筛这套写法一行都不用改。

这段是被真实报错改写的

这节课最初写的是「第一个块的文本在 resp.content[0].text」。你用 kimi-k3 跑自检时撞上了 ThinkingBlock 报错，证明那个简化写法是错的。
记住这个教训的形式比记住结论更值钱：凡是「取第一个」的假设，在真实 API 面前都很脆弱。你会在整个职业生涯里反复遇到它。

关键实验：模型没有记忆

脚本会做三件事：

  1. A　问一个普通问题：list 和 tuple 有什么区别。
  2. B　不带任何历史，直接问「那前者的常见用途是什么？」
  3. C　把 A 的问答补进 messages，再问同一个问题。

B 的回答会明显语焉不详甚至反问你「前者指什么」。C 会答得好好的。两次请求发的是同一句话，模型也是同一个。

结论只有一句，但它是整个 Agent 工程的地基：

今天要装进脑子的一句话

模型是无状态的。服务端不替你存任何东西。
它每次「记得」上文，都是因为你把全部历史重新发了一遍。

所以脚本最后会自动帮你算一个比值：带历史时的 input_tokens 是不带时的多少倍。这个数字随对话轮数持续增长，而输入 token 是按量计费的。

把这条推到你的目标上：客户说「做一个能一直聊的客服机器人」，你要立刻在脑子里算的是第 50 轮的单轮成本，而不是第 1 轮的。第 1 轮几乎免费，第 50 轮可能贵几十倍。不懂这一点的人报不出正确的价，要么亏钱，要么报得离谱丢单。

具体单价我没法在这里给你：这台机器打不开 Anthropic 的定价页（docs.claude.com 和 platform.claude.com 都不可达，只有工程博客和 GitHub 能通）。跑完脚本后去 console.anthropic.com 看 Usage 页，那里是权威数字，顺便确认这次实验确实只花了零点几分钱。

卡住了？先看这里

ModuleNotFoundError: No module named 'anthropic'：忘了 source .venv/bin/activate。看提示符前有没有 (.venv)。

「没找到 ANTHROPIC_API_KEY」：环境变量没设，或者设在了另一个终端窗口。

AuthenticationError / 401：key 无效，或者 key 和 ANTHROPIC_BASE_URL 不匹配（拿中转的 key 打了官方地址，或反过来）。

NotFoundError / 404：模型名这家供应商不认，或者 base_url 多写了 /v1/messages。用 LESSON_MODEL 换个模型名试试。

APIConnectionError：地址连不上。中转地址拼错，或这个域名从你的网络访问不到。

AttributeError: 'NoneType' object has no attribute 'content'：TODO 1 没填，resp 还是 None。

AttributeError: 'ThinkingBlock' object has no attribute 'text'：写成了 resp.content[0].text，而第一个块是思考块。按类型筛：if b.type == "text"。

TypeError: 'TextBlock' object is not subscriptable：写成了 resp.content[0]["text"]。内容块是对象不是 dict，用点号。

回复被截断，或者没有文本块：max_tokens 到顶了。思考型模型的 thinking 也算输出 token，所以给 800 而不是 300。resp.stop_reason 会显示 "max_tokens" 而不是 "end_turn"。

参考答案（自己写完再打开） 
def ask(messages):
    resp = client.messages.create(
        model=MODEL,
        max_tokens=800,
        messages=messages,
    )

    # 按类型筛，不要假设第一个块是文本
    text = "".join(b.text for b in resp.content if b.type == "text")
    used = (resp.usage.input_tokens, resp.usage.output_tokens)

    return text, used

四行。第 1 课的循环是 11 行，加上这 4 行，你已经有了一个真正能跑的 Agent 的全部零件，只差把它们接起来（下一课的事）。

今天的主要阅读

Building Effective Agents — Anthropic 工程博客（我已确认这个链接可以打开）

上节课我只能转述，因为当时抓不到原文。现在拿到了，这是文章里划定边界的原句：

Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks.

Anthropic, Building Effective Agents

翻译：workflow 是「LLM 和工具被事先写好的代码路径编排起来」的系统；agent 则是「LLM 自己动态决定流程与工具用法、自己掌控如何完成任务」的系统。

还有一句同样值得抄下来，它是这篇文章真正的忠告：“we recommend finding the simplest solution possible, and only increasing complexity when needed. This might mean not building agentic systems at all.” 翻译：先找最简单的方案，只在确有必要时才加复杂度，这甚至可能意味着根本不该做 Agent。接活的时候，能判断「这个需求不需要 Agent」是很值钱的能力。
