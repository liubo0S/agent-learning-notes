裁剪：不能随便砍

第 2 课的结论还在起作用：模型无状态，messages 就是它能看到的全部世界。历史一直涨，早晚会撞上 model_context_window_exceeded（协议速查里列过这个 stop_reason）。最直接的应对是：发请求前，先把历史裁掉一部分。

但不能按"条数"随便砍。回想第 3、4 课反复强调的那一点：tool_use 和 tool_result 必须成对出现。一轮工具调用在 messages 里长这样：

[..., {role: "assistant", content: [tool_use, ...]}, {role: "user", content: [tool_result, ...]}]
裁剪的单位是"一对"，不是"一条"

如果你按条数裁，恰好砍掉一半（留下 tool_use 那条，砍掉 tool_result 那条，或者反过来），服务端会立刻报 400，因为出现了配不上对的块。必须整对一起留下或者一起砍掉。这是「取第一个不可靠」那条原则的第三次出场：任何时候把 messages 当成"随便切片的列表"都会踩坑。

另外第一条消息永远保留：那是用户最初的问题，砍掉它，模型连自己在回答什么都不知道了。

def trim_history(messages, limit):
    if len(messages) <= limit:
        return messages
    head = messages[:1]       # 最初的问题，永远留着
    body = messages[1:]
    while len(head) + len(body) > limit and len(body) >= 2:
        body = body[2:]        # 整对砍掉最早的一轮
    return head + body
这是一笔真实的取舍，不是免费的午餐

裁掉的历史里可能藏着模型早些轮次查到的信息（比如"杭州 26 度"这句话）。裁掉之后，如果最终答案需要回溯到那条信息，模型可能就说不完整了，或者要重新查一次（多花一次工具调用的钱）。裁剪省的是 token 成本，付出的代价是可能丢掉早期上下文。这笔账要不要划算，取决于你的场景：客服机器人可能可以接受"忘了三十轮前的闲聊"，但一个需要长期记住用户偏好的助手就不行。跟客户报价、定方案时，这是要摆到桌面上的权衡，不是纯技术细节。

结构化日志：换个去处，不换心智

前几课一直在用 print() 看执行过程，这在教学时够用，但接给客户的项目里，print() 出的字符串没法被日志系统检索、按字段筛选、拉图表。换成一行一个 JSON：

def log(event, **fields):
    print(json.dumps({"event": event, **fields}, ensure_ascii=False))

**fields 这个写法你在第 1 课就学过（fn(**call.input) 的同一个星号），这里反过来用：把任意多个关键字参数收集成一个 dict。TS 里最接近的类比是 { event, ...fields } 的对象展开。

关键点不是格式好看，而是去处变了、代码结构没变：以后接真实项目，把这行 print 换成你日志库的调用（比如 Python 标准库的 logging，或者某个云平台的 SDK），调用这个 log() 函数的所有地方一行都不用改。这是"面向未来但不过度设计"的一个具体例子：今天用最简单的 print，接口留对了，以后升级零成本。

插在哪几个点

不是每一行都要记日志，那样反而没法看。今天只插两个点：

  • 每次执行工具之后：工具名、参数、结果、是否报错。这是你排查"客户说 Agent 干了错事"时第一个要看的记录。
  • 每次真的发生裁剪之后：裁前裁后各多少条消息。这能让你事后回答"这次对话是不是丢了上下文"这个问题。

还剩什么（先想，别写）

裁剪是最简单的一种应对方式，粗暴但可控。更精细的做法是摘要：不是直接砍掉旧历史，而是用模型把旧历史压缩成一段短总结，替换掉原文再继续对话。想一下：

  • 摘要比裁剪好在哪里？又贵在哪里？（提示：摘要本身也要调用一次模型）
  • 如果客户说"绝对不能丢任何历史信息"，裁剪和摘要都不满足，你还能给出什么方案？

今天的主要阅读

没有新的外部链接。今天的裁剪逻辑纯粹是列表操作，用你已经会的 Python 就能验证：

python -c "m=[1,2,3,4,5]; print(m[:1] + m[1:][2:])"

这行会打印 [1, 4, 5]，和 trim_history 里那一步做的事完全一样，只是换成了数字。想不清楚裁剪逻辑时，先拿这种简化过的假数据在 python3 交互模式里试一遍，比直接改真实代码调试快得多。
