唯一的新概念：模型看不见你的代码

第 1 课里，fake_model 凭空就知道有 get_weather 和 add，因为是我写死的。真模型不知道。它看不到你的 Python 文件。

所以你得用一份声明告诉它：

{
    "name": "get_weather",                  # 必填。要和你的函数表键一致
    "description": "查询某个城市当前的天气。当用户问到天气、气温、冷热时使用。",
    "input_schema": {                        # 必填。标准 JSON Schema
        "type": "object",
        "properties": {
            "city": {"type": "string", "description": "城市名，例如「杭州」"},
        },
        "required": ["city"],
    },
}

这个结构你不陌生。input_schema 就是 JSON Schema，和你在前端做表单校验、写 OpenAPI 时用的是同一套东西。

今天最重要的一句话

description 不是注释，它是提示词。
模型完全靠这句话判断「现在该不该用这个工具」。写得含糊，模型就选错或者干脆不用。
而这不是代码 bug，是提示词问题。

这条对你的目标很实在。交付之后客户报「它没去查天气」，你得能立刻分辨：是循环写错了，还是 description 没说清「什么时候用」。这两种问题的排查方向完全相反，分不清就会浪费掉一整天。

顺带一个写声明的经验：description 里写「什么时候该用它」，比写「它做什么」有用得多。「查询天气」不如「当用户问到天气、气温、冷热时使用」。后者直接给出了触发条件。

请求和回复的变化

请求只多了一个参数：

resp = client.messages.create(
    model=MODEL,
    max_tokens=1024,
    tools=TOOL_SCHEMAS,        # ← 新增这一行
    messages=messages,
)

回复多了一种可能。stop_reason 会变成 "tool_use"，content 里出现 tool_use 块：

tool_use 块的字段用途
.name工具名。拿它查你的函数表
.input参数，一个 dict。fn(**block.input) 展开调用（第 1 课那个 **）
.id本次调用的标识。报结果时必须原样带回

筛出它的写法你已经会了，和第 2 课筛 text 块一模一样，只换类型名：

calls = [b for b in resp.content if b.type == "tool_use"]

最容易漏的一步

执行完工具，把结果发回去之前，必须先把模型这一轮的完整回复原样追加回 messages：

messages.append({"role": "assistant", "content": resp.content})
messages.append({"role": "user", "content": results})

为什么？因为第 2 课那个结论：模型是无状态的。它不记得自己刚才要求调了什么工具。你只发结果不发请求，服务端会直接报 400，说 tool_result 找不到对应的 tool_use。

那个「模型没有记忆」的实验，今天开始变成每天都要处理的工程约束。

两个反直觉的地方

1. 工具结果用 role: "user" 发回去。不是 assistant，也没有 "tool" 这个角色。想通就好记：结果不是模型说的话。（OpenAI 的接口里有 tool 角色，Anthropic 这套只有 user 和 assistant，读文档时别混。）

2. 两个方向的数据类型不一样。模型给你的块是 SDK 对象，用点号取值 block.input；你给模型的块是 普通 dict，用键构造。字段名也不对称：一个叫 id，另一个叫 tool_use_id。

{
    "type": "tool_result",
    "tool_use_id": call.id,      # ← 用 .id 配对，字段名却叫 tool_use_id
    "content": str(output),       # ← 要字符串，数字得 str() 一下
}

完整的字段清单和报错对照表我整理成了 工具调用协议速查，写代码时开着它。

  3. 补 TODO 1：照 WEATHER_SCHEMA 的样子，给 add 写声明。数字类型写 "number"。
  4. 补 TODO 2：筛出 tool_use 块。
  5. 补 TODO 3：把 resp.content 原样追加为 assistant 消息。
  6. 补 TODO 4：构造 tool_result 块。
  7. 运行 python3 exercises/03_real_tool_loop.py

脚本会问三个问题。重点看第三个：「杭州今天几度？在那个温度上再加 7 度是多少？」

这一问模型必须先查天气，从返回的文字里读出 26，再拿 26 去调 add。你会看到两轮 tool_use，第二轮的参数是第一轮结果推导出来的。

那一刻就是 Agent 和「一次函数调用」的分界线：没有人告诉它要分两步，是它自己决定的。这也正是 Anthropic 那篇文章里 agent 的定义所指。

顺便注意每轮打印的 输入 token：它会一路往上涨，因为历史在累积。第 2 课算过的那个比值，现在你能亲眼看着它变大。

卡住了？先看这里

400，说 tool_result 找不到对应的 tool_use：TODO 3 漏了，没把 assistant 那一轮追加回去。这是本课头号错误。

400，说少了 tool_result：模型一轮要了两个工具，你只报了一个。calls 要全部遍历。

KeyError: 'add'：TODO 1 里的 name 和 TOOLS 的键不一致。

TypeError: add() got an unexpected keyword argument：input_schema 里的属性名和 Python 函数的参数名不一致。函数是 add(a, b)，schema 里就得是 a 和 b。

模型不肯用 add，自己算了：description 不够明确。试试写「计算两个数字相加。需要做加法运算时使用，不要自己心算。」这就是提示词工程，不是代码问题。

某些端点报 tools 相关的 400：第三方中转对工具支持可能不完整。改两个环境变量换供应商，Python 代码不用动（第 2 课学的）。

循环跑满 6 轮还没停：看看是不是每轮都在重复调同一个工具。通常是 tool_result 的 content 是空的，模型没拿到有效信息。
