术语表

Agent 开发的规范用语。中英并列，因为你查的文档是英文的。

这份表的规矩

这里不是让你背的词典，而是一份「已掌握」的清单。一个术语只有在你用对过之后才会进来。所以它会长得比课程慢，这是刻意的：表上的每一条，你都应该能不看解释就说清楚。
同一个概念在业界常有好几种叫法，本表会挑一个作为标准说法，其余列为避免使用。此后所有课程一律用标准说法。

核心概念

Agent（智能体）：
一个让模型自己决定用什么工具、什么时候收手的系统。判据是控制权归谁：流程由模型动态决定才算 Agent。
避免：AI、机器人、大模型应用（这三个都太宽，指不到具体东西）

Workflow（工作流）：
执行路径由你事先用代码写死的系统，模型只是被编排的一环。它和 Agent 是并列关系，不是低级版本；需求确定时它更可靠也更便宜。
避免：管道、流水线、编排（都不带「路径事先写死」这层含义）

Agent 循环（agent loop）：
「问模型、执行工具、把结果送回模型」这个不断重复的过程，直到满足退出条件。它是 Agent 的全部机制所在。
避免：主循环、事件循环（后者在 Python 里专指 asyncio 的东西，会混）

退出条件（stop condition）：
让 Agent 循环停下来的判断。至少需要两个：模型主动表示说完了，以及一个轮数硬上限。
避免：终止条件、break 条件

工具

工具（tool）：
一个交给模型「可以要求调用」的普通函数。模型本身只能把文字变成文字，工具是它唯一的对外通路。
避免：插件、函数、能力、技能

工具表（tool registry）：
从工具名映射到函数本身的字典。模型说出名字，你查表拿到函数去执行。
避免：工具集、工具箱、函数映射

工具调用（tool call）：
模型输出的一段结构化请求，内容是「我想调用哪个工具、参数是什么」。
关键：这只是一个请求，模型没有执行任何东西。真正执行的是你的代码。API 里对应的块类型叫 tool_use。
避免：函数调用、function call（后者是 OpenAI 的旧叫法，混用会在读文档时出岔子）

消息与上下文

无状态（stateless）：
模型不保存任何跨请求的记忆。它每次「记得」上文，都是因为你把全部历史重新发了一遍。
避免：没有记忆、不会话（前者是口语说法，容易让人以为是模型缺陷而非协议设计）

messages（消息列表）：
一次请求携带的完整对话历史，一个列表。每项含 role 和 content。
因为模型无状态，这个列表就是模型能看到的全部世界。
避免：对话记录、聊天历史、prompt（最后一个尤其要避免，messages 是结构，prompt 是内容）

role（角色）：
一条消息的发出方。本工作区用到的接口只有两个值：user（你）和 assistant（模型）。
注意：工具执行结果也用 user 发送，因为那不是模型说的话。
避免：身份、发言人。另外 OpenAI 接口里的 tool 角色在这套接口里不存在，别混

内容块（content block）：
content 列表里的一项。一次回复可能同时包含多个块，类型各不相同：text（有 .text）、thinking（有 .thinking，没有 .text）、tool_use（有 .name / .input）。
取值前必须按 type 筛，绝不能假设第一个块是文本。
避免：段落、片段、消息体

token：
模型计费和计量的最小单位，大致对应词或字的片段。
input_tokens 随对话轮数持续增长，因为每轮都要重发全部历史。这是长对话变贵的机制。
避免：字数、词数（都不准，且会误导成本估算）。中文习惯直接说 token，不必翻译

上下文（context）：
模型这一次请求能看到的全部内容，即 messages 加上工具声明等。
它有上限（上下文窗口）。超了就必须裁剪或摘要，这是你的代码要做的事。
避免：记忆、背景（「记忆」会和无状态矛盾，尤其要避免）

工具协议

工具声明（tool schema）：
放进请求 tools=[...] 里的一份 JSON Schema，告诉模型这个工具叫什么、什么时候该用、参数长什么样。模型看不到你的代码，全靠这份声明判断。
避免：工具定义、函数签名（后者容易和 Python 函数本身的参数列表混）

tool_use 块：
模型发出的工具调用请求，内容块的一种，是对象，取值用点号：.name / .input / .id。
避免：调用块（太笼统，容易和 tool_result 混）

tool_result 块：
你执行完工具后报回去的结果，是一个普通 dict，用键构造：tool_use_id / content / is_error。放进 role: "user" 消息的 content 列表里。
避免：返回块、结果块（都没体现出它必须用 dict 构造这一层）

tool_use_id：
用来把 tool_result 和它对应的 tool_use 配对的字段。取值来自请求那边的 .id，但字段名不叫 id，这是最容易记混的一对名字。
避免：调用 id、请求 id（不是错，但不是 SDK 里的实际字段名）

stop_reason：
每次回复上都有的字段，说明模型为什么停下这一轮。循环退出条件判断它是否等于 "tool_use"，不是判断是否等于 "end_turn"，否则 max_tokens、refusal 等异常情况会让循环空转。
避免：结束原因（口语化，容易忽略它有好几种取值不只是"结束"）

is_error：
tool_result 块上的可选字段，标记这次工具执行是不是失败了。配合把异常信息塞进 content，模型往往能看懂并自己调整参数重试。
避免：报错标记（不是错，但不是 SDK 里的实际字段名）

人工确认（human-in-the-loop confirmation）：
危险、不可逆的工具（删除、发送、转账）执行前，暂停下来让人确认，拒绝就把这当成一次失败结果报回给模型。教学里用 input() 模拟，真实项目里通常是一次前端交互。
避免：人工审核（听起来更像事后复核，而这里强调的是事前拦截）

会歧义的地方，本表的裁定

「Agent」在业界用得极松，有人拿它指全自动系统，有人拿它指固定流程的实现。本工作区采用 Anthropic 的划分：两者统称 agentic system（智能体系统），其中路径写死的叫 workflow，模型自主掌控的才叫 agent。说「Agent」时一律指后者。

「工具调用」既可以指模型发出的请求，也可能被人用来指整个「请求加执行」的过程。本表只指请求那一半。执行那一半没有专门术语，直接说「执行工具」。
